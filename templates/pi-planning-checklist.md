# SAFe PI Planning — pre-read, agenda and outputs

For a two-day, in-person or hybrid PI Planning with 5–12 teams on one ART.

## 48 hours before

- [ ] Business context presentation circulated (not presented cold on the day)
- [ ] Top 10 features in the ART backlog, prioritised, with acceptance criteria
- [ ] Architectural runway / vision slides shared
- [ ] Team capacity pre-calculated, including leave and support rotation
- [ ] Known dependencies from the last PI listed
- [ ] Logistics: rooms or breakout links, board templates, timers, facilitators per team

| 08:45 | Product/solution vision | Top features, target outcomes |
| 09:30 | Architecture vision and runway | Enablers, non-negotiables |
| 10:15 | **Planning context + draft plan (teams)** | Draft PI objectives per team |
| 12:00 | Lunch | |

| 15:00 | **Draft plan review** | Management/PO feedback, adjustments |
| 16:30 | Management review + Problem-solving workshop | Resolved or parked issues |
| 17:30 | Close | Overnight actions |

## Day 2

| Time | Activity | Output |
|---|---|---|
| 08:00 | Planning adjustments from Day 1 | Revised context |
| 08:30 | **Final plan (teams)** | Final stories, PI objectives |
| 11:00 | **Program board / dependency mapping** | Dependencies with owners and dates |
| 12:30 | Lunch | |
| 13:30 | Final plan review | Confidence vote per team |
| 14:30 | **Confidence vote + ROAM the risks** | Resolved / Owned / Accepted / Mitigated |
| 15:30 | Plan rework where confidence < 3 | Revised commitments |
| 16:30 | ART Planning Board review, retrospective | Actions for next PI |

## Confidence vote

Each team votes 1–5 on whether they can deliver their PI objectives. Anything below
3 is not a failure — it is information. Rework the plan until it reaches 3, or
explicitly record what is being descoped. Do not average the votes into a single
programme number; you lose the team that is in trouble.

## PI objectives, written properly

Each objective is a business outcome with a value assigned by the business owner:

- *"Reduce manual refund handling to near zero for the top three failure reasons"* — 8
- *Not*: "Deliver stories 1–24" — that is a list, not an objective

Committed objectives are promises. Uncommitted objectives are stretch, and they are
allowed to slip without a crisis meeting.

## ROAM

| Letter | Meaning | Requirement |
|---|---|---|
| R | Resolved | Happened already / no longer a risk |
| O | Owned | One named owner, plan to address |
| A | Accepted | We live with it; stated impact |
| M | Mitigated | Action taken, residual risk stated |

Anything not ROAMed on the program board is a risk the ART has silently accepted —
usually the one that bites in week three.

## Outputs checklist (end of Day 2)

- [ ] PI objectives per team, committed and uncommitted separated
- [ ] Program board with cross-team dependencies, owners and dates
- [ ] Risks ROAMed
- [ ] Confidence votes recorded per team
- [ ] Team PI calendars agreed, including iteration and system demo dates
- [ ] Retro actions from the planning event, owned and dated
